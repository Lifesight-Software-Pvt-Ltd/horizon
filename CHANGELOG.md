# Changelog

All notable changes to `horizon_forecaster` are documented here.
Format loosely follows [Keep a Changelog](https://keepachangelog.com/).

## [Unreleased]

### Fixed

- **Text dates were sorted alphabetically, not by time.** The constructor sorted the raw date column before parsing it, so text such as `01/15/2023` sorted ahead of `12/20/2022`. The train/validation/test windows then mixed up the calendar and the forecast started from the wrong date, with no error. The date column is now parsed first (`utils.parse_date_column()`), on a copy — the caller's DataFrame is never modified — and everything downstream sorts and splits on real dates.
- **Duplicate dates were accepted silently.** Prophet and NeuralProphet then failed and dropped out of the run, SARIMAX and CatBoost counted the repeat as an extra period, and duplicates inside the test window made `evaluate()` fail late with an unrelated ensemble-alignment error. Duplicates now raise `InvalidConfigError` at construction, naming the dates.
- **A future driver table that did not fit the forecast was used anyway.** `forecast(future_independent_data=...)` reads the table by position, and each model reacted to a bad table differently, while the run still finished. Too few or too many rows made Prophet and SARIMAX fail and CatBoost carry the forecast alone. A misspelled column was ignored and the real driver silently auto-generated. A blank value or text made two models drop out; an infinite value gave Prophet a NaN forecast; a negative spend made SARIMAX fail; a promo flag of 2 doubled Prophet's promo effect while the other models treated it as 1. A date column was never looked at, so a table starting a week late, or in reverse order, was applied row by row to the wrong periods. A dict or Series failed with a raw `AttributeError`, and a table passed to a forecaster with no drivers was ignored. Each of these now raises `InvalidConfigError` with the reason, before any model runs (`future_exog.check_future_table()`).
- **A failed `forecast()` left the previous call's results in place.** `forecast_ensemble`, `forecast_errors` and `future_exog_used` are now cleared at the start of every call, so a call that raises cannot leave an earlier forecast looking like its own.
- **A driver that never changed inside a fit window broke NeuralProphet and Prophet.** A driver can vary over the full history — so it survives the zero-variance check — yet be one value throughout the training window, e.g. a price change or new promotion that first appears in the validation weeks. NeuralProphet discarded such a column when fitting and then rejected it when predicting (`ValueError: Unexpected column ... in data`), so it dropped out of the run, reported on client data with a `Price_Hike` flag. Prophet, when the constant value was not 0, fitted an arbitrary effect to it — +31,403 on a series around 3,500 whose true effect was −400 — while CatBoost, SARIMAX and Bayesian PyMC gave it no effect. Such a driver is now left out of that window's fit for every model, so all of them give the honest answer (no effect yet) and stay comparable. A warning names the driver, its value and the date it first changes, and says which score includes the effect no model could see: the validation MAPE for the training window, the test MAPE for the train+validation window. `forecast()` refits on the full series and uses the driver as before.
- **Two-value quantities were treated as event flags and set to 0 for the whole forecast.** Auto-detection counted any driver with at most two distinct non-negative values as a flag, and generated flags default to 0. So TV spend of 0 or 5,000 was forecast at 0, a 0%/20% discount at 0, a 0.5/1 column at 0 (a value it never takes), and a price of 9.99 or 12.99 at 0 — a free product. Only columns whose values are 0 and 1 are now auto-detected as flags; every other column follows `future_exog_strategy`. `event_columns` still names flags explicitly.

### Added

- **Example notebooks and the research paper.** `examples/` adds two runnable notebooks with their outputs saved: `daily_website_traffic.ipynb` (three years of daily web traffic, with known calendar drivers supplied and ad spend generated) and `weekly_marketing_mix.ipynb` (a week × region × product marketing-mix panel totalled to one weekly series, forecast a quarter ahead against a supplied media plan). Both run unchanged in Colab and use simulated Kaggle datasets, committed exactly as downloaded and credited in `examples/README.md` and `NOTICE`; all preparation happens in the notebooks. `examples/paper/` holds the current version of *Robust Ensemble Forecasting in Practice*, also linked from the README.
- **`date_format` parameter on `HorizonForecaster`.** Without it, the date column is detected: datetimes pass through, and text must be one of `YYYY-MM-DD`, `YYYY/MM/DD`, `DD-MM-YYYY`, `DD/MM/YYYY`, `MM-DD-YYYY`, `MM/DD/YYYY` or a full ISO timestamp, the same format on every row. A column that is valid both day-first and month-first (every day and month 12 or less) raises instead of being guessed — real exports have been silently read month-first. Mixed formats, two-digit years and numeric date columns also raise, each with a specific message. `date_format` settles the ambiguous case and accepts any other strftime pattern.
- **A warning when dates are missing.** Data that passes the acceptance contract below can still have scattered gaps (weekday-only sales, an occasional missing day). These are reported with the share of periods present, the number of gaps and the longest one, and the run continues. The warning says what gaps affect: windows are counted in rows, and SARIMAX treats consecutive rows as consecutive periods. Horizon still never fills gaps itself.
- **Warnings for future driver values the models cannot be trusted with.** A supplied value outside a driver's historical range warns, naming what each requested model does with it — Prophet and NeuralProphet extend the effect in a straight line, SARIMAX and Bayesian PyMC cap it at the historical range, CatBoost treats it like the most extreme value it has seen. In testing, ten times the usual spend gave 5,058 from Prophet against 1,682 from CatBoost and 1,764 from SARIMAX. A supplied column for a declared driver that was dropped for never changing in the history also warns, since its values are ignored.
- **Future driver tables may carry dates.** A date column (or a `DatetimeIndex`) in `future_independent_data` is now checked against the forecast dates instead of being ignored. Text dates are read like the history's; when a short table is ambiguous between day-first and month-first, the reading that matches the forecast dates is used.
- **On/off text in driver columns.** `true/false`, `yes/no`, `y/n`, `t/f` and `on/off`, in any case and mixed freely, are read as 1/0 in the data and in `future_independent_data` (on a copy; the caller's DataFrame is unchanged). Other text now raises an error saying what is unclear instead of the generic "missing or non-numeric values": two other words such as "Promo"/"None" (Horizon cannot tell which means "on", and guessing wrong would flip every learned effect), categories such as "Low"/"Mid"/"High", a single word with blanks, or text among numbers such as "1,200", with the date it appears on.
- **A warning when `carry_forward` would hold a promotion week.** If a generated driver's last value is at least 1.5× or at most 0.5× its median over the previous 13 weeks (28 days for daily data), or an event flag is 1 in the last period, the warning names the driver, its value and its usual level. In testing, a last week of 16,000 spend against a usual 6,000 lifted an 8-week forecast by 15%; on real data (Goodr) the forecast came out at 1.6–2.5× the same period last year.
- **A warning when a generated event flag misses last year's events.** If a flag is generated rather than supplied and was 1 within a week of the same date last year, the warning names those dates and asks for known events to be supplied — a generated flag is 0 throughout, and `seasonal_naive` repeats flags by week number, which puts a moving holiday such as Black Friday in the wrong week. Homemakers' forecast missed Black Friday this way.

### Changed

- **The date column now has to meet an explicit acceptance contract, and anything else raises.** Beyond parsing and duplicates: every step between dates must be a whole number of periods (weekly dates on one weekday, daily dates whole days apart); more than half of the steps must be exactly one period; and no more than 4 weeks (`MAX_CONTINUOUS_GAP_DAYS = 28`) of dates may be missing in a row. Previously a declared frequency the data contradicted (weekly data declared daily, or the reverse), and spacing Horizon does not support (every 2 days, fortnightly, monthly), only warned — and the run went on to produce forecast dates, window sizes and model settings for the wrong frequency. In testing, monthly data declared daily finished with a 0.67% MAPE and a daily-dated forecast. A mis-declared frequency now raises `InvalidConfigError` naming the right one; unsupported spacing raises `UnsupportedFrequencyError`. The gap limit is absolute rather than a share of the history, because a long hole does the same damage in four years of data as in two, and it is enforced separately from scattered gaps, which hurt far less. Two existing tests that asserted "warn, don't block" for irregular spacing and a frequency mismatch now expect these errors.

## [1.0.0] - 2026-09-03

The first public release, and the first stable API.

The entries below record the rework that produced it, against the private
pre-release state of the library. They are kept rather than collapsed into a
single "initial release" line because they say *why* the shipped API is shaped
the way it is — why selection and reporting live in different windows, why the
default combination rule has no weights, why `evaluate_ensemble` is a dict. The
changes land together on purpose: each addresses a defect the others would
otherwise re-introduce.

### Fixed

- **SARIMAX produced degenerate forecasts on any series it did not difference.** `_fit_one()` never passed a `trend` argument, so statsmodels applied its default of no constant term. That is correct for a differenced series — differencing removes the level, and a constant would imply an unrequested drift — but with `d=0` and `D=0` it means fitting a **zero-mean process**, and this wrapper fits in `log1p` space where a typical business series sits around 7. The optimiser's only escape is to push the AR root to ~1 so the level decays as slowly as possible; the fit then looks respectable in-sample while the forecast mean-reverts toward zero. Measured on synthetic daily data: a trending series scored **98.2% MAPE**, with an 80-period forecast falling from ~945 to 3.3 against actuals near 1,300; a **flat** series scored **97.8%**. Over a shorter 28-period horizon the same defect merely halved the forecast, which is more dangerous still — it reads as a plausible downturn rather than an obvious failure, and the existing divergence guard only watches for explosions upward. `SARIMAXWrapper._trend_for()` now selects `"ct"` (constant and linear trend) whenever nothing is differenced, taking the trending case to ~6–7% and the flat case to ~3.9%. A constant alone was tried first and was not enough: it stops the collapse to zero but leaves the forecast reverting to the training mean, which on a growing series is still a confident prediction of decline (~30%). The change is deliberately narrow — the differencing decision is untouched, so every series that already received `d>=1` fits exactly as before. Surfaced by the three-way split below: the same hyperparameters scored 1.90% on validation and 95.06% on test, and a gap that size is not model error.
- **Bayesian PyMC clamped every prediction at zero unconditionally.** The back-transform in `predict()` applied `np.clip(..., 0.0, None)` regardless of the data, so any target that legitimately goes negative — net revenue after refunds, inventory deltas, week-on-week change — had every negative prediction silently rewritten to 0. Not a conservative approximation but a wrong number presented with full confidence. Now data-driven, matching the rule `CatBoostWrapper` and `NeuralProphetWrapper` already applied: the floor is kept only when the training target was itself never negative.
- **The `sarimax:` block in `default_params.yaml` carried two contradictory comment headers**, the first stating the model has no `hyperparameter_grid` and self-tunes internally — untrue since SARIMAX moved to the shared grid search — immediately above the corrected block saying the opposite. The stale one is removed.
- **`exporters.build_final_forecast_table()` raised `AttributeError` on the dict a forecaster actually produces.** It was the last public consumer not routing its input through `as_ensemble_dict()`, so a caller holding `forecaster.forecast_ensemble` (a `Dict[str, EnsembleResult]`) and calling the documented builder directly got `'dict' object has no attribute 'combined'`. It survived inside `export_forecast_csvs()` only because that function unwraps the dict before calling it, which is why the shipped one-call path kept working and the hole went unnoticed. Now normalised like every sibling; given several methods it tables the first, matching `plotting._primary_ensemble`.
- **A scalar `ensemble_mape` fallback was stamped onto every method in a multi-method run.** In the `forecast()` context no `EnsembleResult` carries its own MAPE, so a run with `ensemble_method=None` reported one borrowed score against three materially different combined series — fabricating exactly the side-by-side comparison `model_summary.csv` exists to support. The fallback is now used only when a single method was built; with several, the combined rows are still written (with their `rule_applied` and status) but their `mape` is left blank.
- **A forecast breaching both plausibility bounds only reported the upper one**, because the two checks were chained with `elif`. A wildly oscillating forecast could exceed the historical maximum *and* fall below the historical minimum while the user saw only half of it. The checks are now independent.
- **The forecast charts labelled the combined line `"ensemble forecast"` regardless of which rule ran**, while the evaluation charts already named it via `_ensemble_label()`. A degraded two-member plain mean was therefore indistinguishable from a five-member trimmed mean on a forecast plot — the exact thing `degraded` exists to make visible. `plot_forecast()` and `plot_forecast_per_model()` now use the same label; the returned dict key stays the plain `"ensemble"`, since it is a stable handle and a filename.
- **Bayesian PyMC failed on every fit on current macOS toolchains.** PyTensor (PyMC's compiler) appends `-ld64` to its compile commands on macOS 15+, to select Apple's classic linker; recent Xcode / Command Line Tools releases removed that linker, so clang parses the flag as `-l d64` and every compile fails with `ld: library 'd64' not found`. The other models kept running thanks to partial-failure isolation, so the symptom was Bayesian PyMC silently missing from every run. Upstream is [pytensor#2268](https://github.com/pymc-devs/pytensor/issues/2268), with no released fix, and the PyTensor pin cannot move (PyMC 5.25.1 requires `pytensor<2.32`, and newer PyMC needs numpy 2, which `neuralprophet==0.8.0` forbids). The new `horizon_forecaster.models._pytensor_compat.ensure_macos_linker_compat()` runs before the first PyMC model is built: on macOS only, it links an empty program with `-ld64` using PyTensor's configured compiler, and only if that fails with exactly this error does it drop that one flag from `GCC_compiler.compile_args`. Toolchains that accept the flag are left untouched, a user-configured `cxx` is respected (and an empty `cxx` disables the check), and the decision is made once per process. See [`docs/installation.md`](docs/installation.md#macos-bayesian-pymc-and-the--ld64-linker-flag).
- **Documentation corrected against the shipped API.** `docs/quickstart.md` and `docs/ensemble_methods.md` had not been updated for this release and still showed the removed `ensemble_weighting` parameter, `training_size` as the primary split control, `evaluate_ensemble`/`forecast_ensemble` as single objects rather than dicts, an `EnsembleResult.weighting` field that no longer exists, and the internal-`evaluate()` behaviour `forecast()` no longer has — several of those examples raised `TypeError` or `AttributeError` as written. `docs/supported_models.md` said hyperparameter selection was scored on the test split, which is the precise defect this release fixes. `docs/installation.md` still told readers to `pip install -r requirements-dev.txt`, a file this release removed.
- Assorted comment and docstring corrections verified against the code beside them: `exceptions.py` named attributes (`reason`, `values`) that no class defines and credited the wrong module with building the rejected-models report; `metrics.mape()` advertised "near-zero" handling it does not implement (the test is for an exact zero); `EvaluationResult.grid_search_summary` documented `None` as meaning "an override was used" when the insufficient-data fallback also returns `None`; the short-training-window warning said affected models "cannot be evaluated" when the train+validation refit sees more rows and often succeeds; `models/base.py` documented a `future_exog=None` path every wrapper rejects, omitted the shape-check exception every wrapper raises first from `fit()`'s contract, presented `target_column` as meaningful when no wrapper reads it, and promised `set_params()` re-targets the next `fit()` for three wrappers that snapshot their parameters at construction; and four comments in `default_params.yaml` were stale or self-contradictory (a "Unlike sarimax" claim contradicted 60 lines above, an epoch range that excluded its own grid, a duplicated parenthetical describing a change that was reverted, `alpha` called an interval width rather than a significance level, and `eval_metric` described as what CatBoost optimises).

### Changed

- **Dependency pins updated during pre-release testing**, each verified against the full test suite: `prophet` 1.3.0 → 1.5.0, `statsmodels` 0.14.6 → 0.15.0, `matplotlib` 3.10.6 → 3.10.9 (still on the 3.10.x line, which keeps Python 3.10 support).
- **Data is now split into three chronological windows: train, validation and test.** Hyperparameter grid search, `mape_threshold` screening and inverse-MAPE weighting all score on **validation**; the winning candidate is refit on train+validation and scored once on **test**, which no selection path is allowed to read. Previously a single held-out window did both jobs, so the MAPE `evaluate()` reported was the same number candidates had been selected to minimise — a selection score, not an out-of-sample estimate, and optimistic by construction. Screening and weighting inherited the same window. `EvaluationResult` now carries both: `mape` is the reported test score and `validation_mape` the selection score, because the gap between them is itself the diagnostic for how much selection overfitting occurred.
  - The refit on train+validation before scoring test is deliberate and costs one extra fit per model. Fitting on train alone and predicting straight across both windows is cheaper, but measures a model trained on less data than would ever be deployed; refitting on everything available makes the reported MAPE an estimate of the same procedure that produces the real forecast.
  - `EvaluationResult.fitted_model` is consequently the train+validation refit — the model that actually produced `test_predictions` — not the train-only fit used during selection.
- **`training_size` is replaced by `validation_size` and `test_size` as the primary way to size the split.** Each accepts an `int` (periods), a `float` strictly between 0 and 1 (a fraction), or `None` for a frequency default: **56 validation / 28 test** for daily, **26 / 13** for weekly. Training takes whatever is left.
  - The defaults are absolute rather than percentages because a percentage makes both windows scale with however much history the caller happens to have, which is the wrong driver for either. The test window estimates the error you will experience when you actually forecast, so it should be about the length of a horizon somebody would really act on; at 15% of a 1,095-row daily series a percentage rule instead yields a 164-day test window, whose score is dominated by far-horizon degradation and is not comparable to the same 15% of a 120-row weekly series. The validation window is a selection instrument that must rank 3–18 candidates, so it wants stability — hence twice the test window rather than matching it.
  - `training_size` survives as a percentage-only alternative route, meaning exactly what it always did (50–100, or 0.5–1.0), with the remainder divided two-thirds to validation. It is **mutually exclusive** with `validation_size`/`test_size`; passing both raises `InvalidConfigError` rather than letting one silently win. It remains percentages only — `training_size=80` is 80%, never 80 periods — so no existing call quietly changes meaning.
  - On a series too short for the defaults they scale down proportionally, capped at 40% of rows between them, preserving the 2:1 ratio and warning with the resulting sizes plus the caution that scores from windows that small are not comparable to scores from a longer series. This binds below roughly 210 daily rows or 98 weekly. Explicitly requested sizes are never silently shrunk — they are honoured or they raise.
- **The default combination rule is now a trimmed mean**, and `ensemble_weighting` is renamed `ensemble_method` since "weighting" is wrong for a rule that has none. Per period the members are sorted, the highest and lowest discarded, and the rest averaged. Estimated weights must be estimated from something, and everything available to estimate them from is a finite sample of past error; a trimmed mean consumes no such quantity, so it cannot leak from a scoring window by construction and has no weights to get wrong. On the external evaluation, inverse-error weighting was also the worse performer on tail behaviour specifically (maximum error ratio 3.74 vs 2.63, maximum regret 2.98 vs 1.59). `inverse_mape` and `equal` remain available and unchanged in behaviour.
  - `ensemble_method` accepts a single name, a list, or `None` meaning "build all three". Combination is arithmetic over predictions already in memory — the fits happened long before — so asking for every rule costs essentially nothing beyond the first, and comparing them on your own series no longer means re-running the fits.
  - The rule names itself accurately via `rule_applied`: over exactly four members, trimming the high and the low leaves two values whose mean **is** the median, and it reports `"median"` rather than calling everything a trimmed mean.
- **`evaluate_ensemble` and `forecast_ensemble` are now `Dict[str, EnsembleResult]` keyed by combination method**, always a dict even when one method was requested — matching the convention the per-model returns already follow, so the shape never depends on how many things were asked for.
- **`EnsembleResult` reworked for rules that have no weights.** `weighting` becomes `method`; `weights` becomes `Optional` and is **`None`** for weightless rules. Not cosmetic: `weights={}` already meant "no member survived", so a trimmed ensemble returning an empty dict would have been indistinguishable from total rejection. New fields: `rule_applied`, `members`, `degraded`, and `trim_shares` — a per-member record of how often each was discarded as the period's high or low value, which identifies *which* model misbehaves and on how much of the horizon, something a weight cannot tell you.
  - The combination step is refactored accordingly. Alignment on `ds` was previously fused into the weighted-sum loop, which meant the loop was driven by the weights dict and a rule with no weights had no way to align anything; it is now a separate matrix builder every rule consumes.
- **Member-failure behaviour is defined.** For the trimmed rule: 3+ members trim normally; 2 fall back to a plain mean; 1 returns that model's own forecast; 0 gives `combined=None`. Three is where the arithmetic stops working rather than a tuned threshold — remove the highest and lowest of two values and nothing remains. Degradation is reported as a first-class `degraded` field rather than a warning, since a two-member plain mean is a materially weaker output than a five-member trimmed mean and should not look identical in a result object. The weighted rules have no such boundary and never report `degraded`.
- **`mape_threshold` is now intended and documented as a filter for degenerate fits, not an accuracy screen.** It still defaults to 40 and still screens, but now also accepts `None` to admit every model. Sweeping the equivalent cutoff from 0.20 to 0.80 on the external evaluation moved the screened rule's mean error by 0.018 total with no monotone trend, and it trailed a simple trimmed mean at every value — so it is kept to catch degenerate fits, not to sort good models from mediocre ones. Screening and trimming both spend robustness: screen five members down to three and the trimmed mean is the median. `0` remains invalid (it would admit only a literally perfect model); since `None` and `0` are both falsy, every internal check tests `is None` explicitly. Screening now reads the **validation** MAPE, like every other decision.
- **`forecast()` no longer runs `evaluate()` internally**, and the `UserWarning` announcing that it was doing so is gone. It needs the winning hyperparameters and a validation MAPE; selection produces both and has to happen anyway before anything can be fitted, so the scores come free and are cached. The previous implementation additionally paid for a test-window prediction it then discarded.
- **A model given explicit `model_params` is no longer failed outright when it cannot be scored on the validation window.** With explicit parameters there is nothing to select, and the fit exists only to produce a score; if it fails — a short series whose training window is below the model's floor, say — the parameters remain usable and `forecast()`, which refits on the full frame, may well succeed. Such a model now carries an undefined (NaN) validation MAPE and warns. A grid search cannot degrade this way and still raises, since with no candidate scores there is no basis for choosing one.
- **A model whose validation MAPE is NaN is now kept by the trimmed rule**, and excluded only by the weighted rules. For `inverse_mape` that is arithmetic — there is no `1 / NaN`. `equal` reads only the member count and could weight such a model, and is excluded on a different ground: a model with no validation MAPE was never screened against `mape_threshold` either, and the weighted rules hand every member a full, untrimmed share, so admitting an unvetted one lets it move the number with no check on it at all. Trimming keeps it because trimming itself bounds any single member's influence. A NaN MAPE usually means every actual in the window was zero (sparse conversions, installs) — the model may have learned the series perfectly well and only the metric broke. Previously such a model was excluded outright.
- **Export filenames and columns changed.** `{prefix}_final_ensemble.csv` becomes `{prefix}_final_ensemble_{method}.csv`, one per rule, suffixed even when only one was requested so downstream jobs can glob a stable pattern. The model summary gains `validation_mape`, `ensemble_method` and `rule_applied`, and carries one row per (model, method) pair plus one per method for the combined result. The rejected-models table gains `ensemble_method`, because exclusion is not necessarily the same across rules.
- **The line charts draw one chart per combination method, and `plot_evaluation()`/`plot_forecast()` return `Dict[str, Axes]` keyed by method** — always a dict, even for a single method, matching the convention the per-model returns and `evaluate_ensemble` already follow, and keyed `"models"` when no ensemble was given. They previously drew only the FIRST requested method: with `ensemble_method=None` a caller paid to build all three rules and then saw one of them, with nothing to indicate the other two existed. Each rule now gets its own chart against the same models and actuals, which keeps the time axis readable without hiding a rule. A caller-supplied `ax` is refused for more than one method rather than silently dropping the rest.
  - `plot_evaluation_per_model()` and `plot_forecast_per_model()` likewise emit one `ensemble_<method>` figure per rule that formed, so five models and three rules give eight figures rather than six. Keys are the method REQUESTED, while the drawn label still names the rule that actually ran — the key is a stable handle and a filename, so it must not change when a rule degrades.
  - `save_evaluation_plots()`/`save_forecast_plots()` (and therefore `export_forecast()`) write `{prefix}_overlay_{method}.png` and `{prefix}_ensemble_{method}.png` per rule. The method suffix is present even for a single rule, for the same reason `final_ensemble_{method}.csv` carries one: a filename that changed shape with the number of rules requested cannot be globbed downstream.
- **`plot_model_comparison()` x-axis labels are rotated**, and the figure widens with the bar count. An "ensemble (inverse_mape)" label is several times longer than a model name and ran into its neighbours at eight bars; rotation anchors each label under its own bar so length no longer decides legibility. The "no ensemble formed" note on this chart now appears only when EVERY requested rule came back empty — with one rule formed and another not, a blanket note would contradict the ensemble bar beside it.
- **`plot_model_comparison()` draws one bar per combination method** when several were built — the one chart that puts every rule on a single Axes, since comparing rules head-to-head is what a bar chart is for. On every chart the combined line or bar is labelled by the rule that actually ran, so a degraded two-member plain mean is never presented as a five-member trimmed mean.
- **Insufficient training rows for some models is a warning, not an error.** It names the models that cannot fit and lets the rest run, per the library's existing partial-failure contract. It deliberately does not raise even when no model can fit on the training window, because the training window does not govern everything — `forecast()` refits on the full series, so 16 rows with a 10-row training window can still produce a real forecast from a model whose floor is 14.

### Added

- `horizon_forecaster/__init__.py` re-exports the public API, so `from horizon_forecaster import HorizonForecaster` works. Importing the package still pulls in none of the heavy backends — each wrapper imports its own lazily inside `fit()`.
- PyPI-facing metadata in `pyproject.toml`: `authors`, `keywords`, Trove `classifiers`, and `[project.urls]`.
- `utils.resolve_split()` and `utils.DEFAULT_EVALUATION_WINDOWS`, covering the split arithmetic and both routes into it.
- `evaluation/ensemble.build_ensembles()`, returning one `EnsembleResult` per requested rule.
- **Python 3.13 support**, alongside 3.10–3.12. Google Colab moved its default runtime to 3.13, which is where a large share of this library's users start, so 3.13 is supported rather than excluded. The full suite has been run on all four versions, and passes identically on 3.12 and 3.13 — same tests, same warnings, and per-model MAPEs matching to two decimals on a seeded five-model run.
  - One caveat, documented in [`docs/installation.md`](docs/installation.md): `neuralprophet==0.8.0` requires `numpy<2`, and numpy ships no 3.13 wheel for its 1.x line, so on 3.13 pip compiles `numpy==1.26.4` from source. That needs a C toolchain (rather than merely preferring one), adds several minutes to the install, and links the system BLAS rather than numpy's tuned build — about 5% slower on a real run, since the time here goes to Stan sampling, torch training and tree building rather than large linear-algebra calls. Verified on Linux x86-64 and macOS arm64. 3.12 remains the faster platform where there is a choice.
- `.flake8`, aligned with `[tool.black]`'s line length of 100 and ignoring the two codes flake8 raises on formatting black itself produces (`E203`, `W503`), plus per-file ignores for the deliberate exceptions in `tests/` (the dependency-import test whose imports *are* the test; the two modules that must call `matplotlib.use("Agg")` or `pytest.importorskip` before importing). The whole codebase is formatted and lint-clean against both tools, so a contributor running them sees only their own diff.
- **Repository tooling.** `.github/workflows/lint.yml` runs `black --check`, `flake8` and `bandit` on every pull request and push to `main`; it is the only automated check. The test suite fits real models and takes 25–60 minutes per Python version, so it is run by hand rather than in CI (see [`CONTRIBUTING.md`](CONTRIBUTING.md)), and there is no publish workflow until the PyPI release process is settled. Dependabot watches GitHub Actions and pip, with ignore rules for the numpy, setuptools and neuralprophet bumps the pins deliberately block. Also: `CODEOWNERS`, issue and pull-request templates, `SECURITY.md`, `CODE_OF_CONDUCT.md` and a `NOTICE` file.

### Removed

- **`requirements-dev.txt`.** It listed `pytest`, `pytest-cov`, `black` and `flake8` — exactly the four packages already declared under `pyproject.toml`'s `dev` optional-dependency group, which is what the docs recommend. Two copies of one list is one more thing to keep in step, and the moment they disagree is the moment it matters. `pip install -e ".[dev]"` is now the single documented way to get the test suite running, covered in [`docs/installation.md`](docs/installation.md). `requirements.txt` stays, mirroring the runtime pins for tools that expect a plain requirements file.

### Still deferred

None of these block a stable API — all are additive:

- Rolling-origin backtesting across multiple origins per series.
- Benchmark-relative metrics (RelMAE against a seasonal-naive reference) and a secondary MASE metric. Both reach into model selection, the threshold and the ensemble weighting at once, so they should be designed as one change rather than separately.
- Family de-duplication of Prophet and NeuralProphet, which share an additive-decomposition methodology (signed-error correlation 0.787, the highest of any pair involving either).
- An error-diversity diagnostic — pairwise signed-error correlation across members, so users can check whether combination has anything to exploit on their own series.
- Non-negativity is **not** enforced library-wide. Prophet can still emit negative point forecasts; SARIMAX is non-negative structurally via its `log1p` fit, and CatBoost, NeuralProphet and Bayesian PyMC clamp only when the training target was itself non-negative.
- 24 CVEs in `torch`/`pytorch-lightning`, forced by `neuralprophet==0.8.0`'s own version constraints.
- The PyPI release. The package installs from a clone today; publishing is the next step.

## Prior development

1.0.0 is the first public release. The library was developed privately before
it, and the entries above describe the API as shipped rather than the route to
it. What that development produced, in short:

- The `BaseAdapter`/`BaseModel` contract and the `MODEL_REGISTRY`-driven
  orchestrator, built so that each of the five models could be added without
  changing `forecaster.py`'s core logic — a rule all five satisfied.
- The five models themselves, each ported from a working reference
  implementation and then corrected where the reference had a defect that
  mattered here: CatBoost's target-lag features (which could not see a demand
  shift coming across a batched horizon) replaced by a trend index plus
  cyclical seasonality; NeuralProphet's autoregressive evaluation (which had
  already seen the actuals it was scored against) held at `n_lags=0`;
  SARIMAX's AIC order selection replaced by MAPE-scored grid search; PyMC's
  whole-series posterior replaced by a train-only fit that reconstructs future
  means from stored draws.
- The pure output and combination layers — `evaluation/`, `future_exog.py`,
  `plotting.py`, `exporters.py` — none of which import a model or the
  orchestrator.
- Packaging hardening driven by real failures rather than caution: exact
  version pins after an unpinned resolve broke on a second machine, an
  explicit package include list after a stray venv folder broke the build, and
  explicit package data after a built wheel was found to be missing the config
  YAML that editable installs had been masking.
- A testing round beyond the unit suite — a synthetic edge-case sweep, an
  invariant fuzzer, and real datasets — which is what surfaced the
  failure-isolation gap, the complete-data requirement, and NeuralProphet's
  under-fitting.

The reasoning behind these, including the diagnoses that were wrong on the way
and the evidence that settled them, is in [`docs/design_notes.md`](docs/design_notes.md).
