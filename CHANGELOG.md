# Changelog

All notable changes to `horizon_forecaster` are documented here.
Format loosely follows [Keep a Changelog](https://keepachangelog.com/); this project has not yet made a tagged release.

## [Unreleased]

### Added

- **Complete-data requirement** (`utils.validate_no_missing_values`): at construction, a **single** missing or non-numeric cell in any column used for training/testing — the date column, the target, or a surviving independent column — raises `InvalidConfigError`. Missing data is never silently dropped or imputed: forecasting requires complete input, so the caller must clean/impute first (matching the project's prior convention — fail loudly rather than forecast on a quietly-shrunk or gap-filled series). Columns present in the DataFrame but not used are ignored. It also checks column *existence* first, so a missing/misspelled date, target, or independent column raises a clear `InvalidConfigError` (listing the available columns) at construction rather than a raw `KeyError` downstream. (Phase 8, real-dataset testing)
- **Future-exogenous-data strategies** (`horizon_forecaster/future_exog.py`, a standalone `FUTURE_EXOG_STRATEGIES` registry of pure functions mirroring `evaluation/ensemble.py`, wired into `forecaster.py` via a new `_resolve_future_exog()`): when `forecast()` is called without (complete) future values for the declared independent columns, they are generated model-agnostically, once, and fed to every model. Selectable via a new `future_exog_strategy` constructor param (validated like `ensemble_weighting`): `carry_forward` (default — hold the last value flat), `recent_average` (mean/median of the last N periods), `historical_average` (**season-aware** — mean/median by day-of-week for daily, week-of-year for weekly), `seasonal_naive` (the seasonal cycle **plus drift** — the fitted trend — so growing seasonal drivers keep growing; falls back to `carry_forward` under one cycle of history), `linear_trend` (fitted line projected forward), and `cycle` (the retained Phase 2 replay-the-tail behaviour). No adapter/wrapper changes were needed — the strategy plugs into the existing model-agnostic future-dataframe step, so the `BaseModel`/`BaseAdapter` gate rule held. (Phase 7)
- **Type-aware event/flag handling** for the future-exog strategies: continuous drivers use the chosen strategy, while binary 0/1 event flags (promos, holidays) default to 0 ("no event unless supplied") — except under `seasonal_naive`, where they follow the cycle so recurring events still repeat. Flags come from a new explicit `event_columns` constructor param if given, else are auto-detected (≤2 distinct non-negative values); the `cycle` legacy strategy is exempt and tiles every column as-is. Also new: `future_exog_aggregator` ("mean"/"median", median being robust to spikes) and `recent_average_window` (N) constructor params. (Phase 7)
- **Partial fill and transparency for future exog**: `forecast()` no longer treats future independent data as all-or-nothing — a supplied column is used as-is and only the missing columns are generated (matching "I know planned spend but not the promo calendar"). The resolved values (supplied + generated, with a `ds` column) are exposed as `forecaster.future_exog_used` and on each `ForecastResult.future_exog_used`, and the auto-generation warning now names only the generated columns and the strategy used. Robustness: NaN-aware aggregation, and non-negative drivers are clipped at 0 so a projected trend can't go negative (drivers that genuinely go negative are left unclipped); out-of-range clamping stays with the adapters. (Phase 7)

- Project scaffolding: package layout, `pyproject.toml`/`setup.py`, CI (`tests.yml`, gated `publish.yml`), dependency spike confirming Prophet, NeuralProphet, SARIMAX (statsmodels), CatBoost, and PyMC import together cleanly. (Phase 0)
- Exception hierarchy (`exceptions.py`): `HorizonForecasterError` base plus 7 typed subclasses with structured attributes. (Phase 1)
- Shared utilities (`utils.py`): zero-variance column cleaning, frequency inference/validation, training-size and MAPE-threshold validators. (Phase 1)
- Evaluation metrics (`evaluation/metrics.py`): MAPE with explicit zero-actual handling (returns `MapeResult`, not a bare float), plus WAPE, RMSE, MAE. (Phase 1)
- Abstract `BaseModel` contract (`models/base.py`), stress-tested against stub versions of all 5 target models; uncertainty bounds (`yhat_lower`/`yhat_upper`) locked in as optional, individual-model-only, never propagated into an ensemble. (Phase 1)
- Data adapters (`data_adapter/base_adapter.py`, `data_adapter/prophet_adapter.py`) reshaping raw data for Prophet, with hard errors (not silent skips) on declared-but-missing columns. (Phase 2)
- `ProphetWrapper`: real fit/predict, regressor handling, Prophet-safe save/load (not generic pickle). (Phase 2)
- Frequency-aware `config/default_params.yaml` (`min_rows_required`: 14 daily / 8 weekly). (Phase 2)
- `HorizonForecaster.evaluate()`: chronological train/test split, fit, predict, MAPE. (Phase 2)
- `HorizonForecaster.forecast()`: full-data refit (once, cached), default future-exogenous-variable strategy (reuse/cycle historical values), horizon-vs-history warning. (Phase 2)
- Default hyperparameter grid search (6 candidates per frequency: 4 tuned + 2 safe `auto` fallbacks) in `evaluate()`/`forecast()`, auto-selecting the lowest-MAPE candidate; exposed via `EvaluationResult.grid_search_summary`. (Phase 2, real-dataset testing)
- Declared-vs-actual frequency mismatch warning in `HorizonForecaster.__init__()`. (Phase 2, real-dataset testing)
- `CatBoostAdapter` (`data_adapter/catboost_adapter.py`): feature engineering built from a trend index (`time_idx`, an absolute day/week offset from a fixed reference date) plus cyclical yearly/half-yearly seasonality (and, for daily data, weekly/monthly seasonality too) via sin/cos encoding, calendar fields, and independent columns passed through as-is. Every feature is computed identically by `transform_train()` and `transform_future()` directly from dates alone — none depend on the target's own recent history, so the adapter needs no "frozen" mechanism for multi-step horizons (see Fixed below for why this replaced an earlier lag/rolling-feature design). (Phase 3, redesigned after real-dataset testing)
- `CatBoostWrapper` (`models/catboost_wrapper.py`): fit/predict via CatBoost's native `Pool`; CatBoost-native `save()`/`load()` (not generic pickle); data-driven non-negative prediction clipping (only applied when the training target was itself always non-negative). (Phase 3)
- `catboost:` block in `config/default_params.yaml`: 18-candidate hyperparameter grid per frequency (16 tuned combinations + 2 safe low-capacity fallbacks), mirroring Prophet's config schema. (Phase 3)
- `HorizonForecaster` generalized from a single hardcoded Prophet model into a `MODEL_REGISTRY`-driven multi-model orchestrator: new `models=` (which registered models to run) and `model_params=` (per-model hyperparameter overrides that skip grid search) constructor parameters. Adding a future model should require only one new `MODEL_REGISTRY` entry. (Phase 3)
- Partial-failure handling in `evaluate()`/`forecast()`: one requested model failing no longer aborts the call for the others. Failures are captured per-call in `evaluate_errors`/`forecast_errors` (reset fresh on each call, not accumulated); `AllModelsRejectedError` is raised only when every requested model fails. (Phase 3)
- `evaluation/ensemble.py`: `build_ensemble()` (pure function, no dependency on `forecaster.py`/model/adapter classes, mirrors `evaluation/metrics.py`'s standalone `mape()`) plus `EnsembleResult`. Combines multiple models' `yhat` predictions into one weighted ensemble, after excluding any model whose MAPE exceeds a configurable accuracy cutoff (`mape_threshold`, an upper bound only — a low MAPE is never excluded). Two weighting strategies: `inverse_mape` (lower-MAPE models get proportionally more weight) and `equal` (every surviving model weighted equally). Operates on the `yhat` column only, per `models/base.py`'s existing design constraint — uncertainty bounds are never combined. Deliberately never raises when every model is excluded by the threshold: returns an `EnsembleResult` with `combined=None` and empty `weights` instead, since the per-model results that produced those MAPEs are still valid and still returned by `evaluate()`/`forecast()` — only the ensemble combination step itself has nothing to combine. Reuses Phase 1's already-defined `ThresholdRejectionError` (per rejected model, unused until now) rather than a new exception type. (Phase 4)
- `HorizonForecaster` gained `mape_threshold` (default `40`; a model is included in the ensemble only if its MAPE is at or below it — an upper cutoff only, with `0.01`/`100` as fixed internal bounds on the value the user can pass, not a symmetric band on model scores) and `ensemble_weighting` (default `"inverse_mape"`) constructor parameters, validated via `validate_mape_threshold`. `evaluate()`/`forecast()` keep their existing `Dict[str, EvaluationResult]`/`Dict[str, ForecastResult]` return shape completely unchanged, and additionally populate `self.evaluate_ensemble`/`self.forecast_ensemble` (an `EnsembleResult`) as a side effect, mirroring how `self.evaluate_errors`/`self.forecast_errors` already work. `evaluate()`'s ensemble also gets its own `MapeResult`, scored against the real held-out actuals — lets you see directly whether the ensemble actually beats the best individual model, rather than assuming a weighted combination is automatically better (see Fixed below: on real testing it wasn't always). (Phase 4)
- `forecast()`'s ensemble always reuses `evaluate()`'s per-model MAPE to decide both weights and threshold rejection, since `forecast()` has no held-out actuals of its own to score future predictions against. If `evaluate()` hasn't been called yet this session, `forecast()` now runs it internally once (emitting a `UserWarning` naming the added cost) purely to derive these weights — a separate fit/split from `forecast()`'s own full-data refit, cached the same way (`self._evaluate_mape_cache`), so it only runs once per session regardless of how many times `forecast()` is called afterward. (Phase 4)
- `plotting.py`: single-axes overlay charts `plot_evaluation()` (held-out actuals vs. each model's test predictions, with per-model MAPE in the legend and shaded uncertainty bands where a model provides them) and `plot_forecast()` (per-model future forecast, optionally over history); `plot_model_comparison()` (bar chart of per-model + ensemble MAPE); and dedicated per-model variants `plot_evaluation_per_model()`/`plot_forecast_per_model()` that give each model (and the ensemble) its own full-size figure so every series stays readable as models are added, rather than overlapping on one axes or being cramped into a faceted grid — these return a `{label: Figure}` dict. `save_evaluation_plots()`/`save_forecast_plots()` render and write the overlay plus one PNG per model/ensemble to disk (closing each figure after writing). Pure, standalone module (no `forecaster.py`/model imports — verified it pulls in neither Prophet nor CatBoost), each function draws onto and returns a matplotlib `Axes` without calling `plt.show()` (caller decides), and colors auto-cycle so unregistered future models chart with no changes here; the ensemble is a fixed red dashed overlay. When an ensemble was requested but none could be formed (every model exceeded `mape_threshold`), the individual-model lines are still drawn but a visible red note flags them as diagnosis-only, so a rejected model isn't mistaken for a trusted/blended result. (Phase 5)
- `exporters.py`: `export_forecast_csvs()` plus three pure table-builders — `build_final_forecast_table()` (the ensemble's blended `["ds", "yhat"]`), `build_per_model_forecast_table()` (every model's forecast stacked into one long table with a `model` column, keeping bounds where present), and `build_rejected_models_table()` (one row per threshold-rejected model: MAPE, threshold, reason). Also standalone/import-light; builders return correctly-columned empty DataFrames rather than raising on empty/None input, so a run where every model was rejected still yields predictable header-only files. Plus `export_forecast()`, a one-call bundle that writes the three CSVs and (by default) the forecast plots into the same folder — matplotlib is imported lazily inside it, so the CSV-only `export_forecast_csvs()` path stays import-light. (Phase 5)
- **SARIMAX** (`data_adapter/sarimax_adapter.py`, `models/sarimax_wrapper.py`, `config/default_params.yaml` `sarimax:` block, registered in `MODEL_REGISTRY`): the third model, and the first to emit prediction intervals (`yhat_lower`/`yhat_upper`). The interval is a constant-variance band (`mean ± z·σ` in log space, using the model's innovation variance `σ²`), NOT `get_forecast().conf_int()`'s horizon-growing forecast variance — over a long forecast the latter makes the log-space interval enormous and `expm1` blows the raw-scale upper bound up to absurd values (a `[8k, 700k]` band around an 80k point forecast). The constant band is a readable, roughly-multiplicative typical-error interval; the ensemble ignores bounds entirely, so this only affects per-model plots/CSVs. Fits in `log1p` space (variance stabilisation) and returns raw-unit `yhat`. The adapter standardises independent columns (auto-`log1p`'ing spend-like ones — non-negative and non-binary — while leaving 0/1 flags linear), clamps future exog to the standardised training range so an out-of-range test value can't extrapolate a fitted coefficient into a log-space blow-up (confirmed on real data: with exog the forecast diverged, without it the same series fit fine; the clamp lets SARIMAX use the exog without diverging), and passes them through unchanged otherwise. Annual Fourier terms are generated in the **wrapper** (not the adapter) so the grid can choose their order per dataset. SARIMAX uses the **standard forecaster grid search** like every other model, varying `(p, q)`, the seasonal `(P, Q)` and `fourier_order_annual`; `d` stays ADF-derived inside `fit()` since it is a property of the data, not a hyperparameter. The winning candidate is refit with `enforce_stationarity=True` (falling back to `False`) to stop explosive AR roots at the source, with a log-space clip as a last-resort guard and a `+σ²/2` lognormal bias correction (constant innovation variance) on the point forecast. The clip is anchored on a high **quantile** of the training target (`clip_anchor_quantile`, default 0.99) rather than its raw max, since on spiky data a lone outlier inflates the cap enormously (a real series with a single 849k spike gave a 3.8e6 cap). The bias correction is configurable via `bias_correction` (default on) — worth knowing it is in tension with the library's own metric: MAPE is minimised by the conditional **median**, which `expm1(mean_log)` already is, while the correction targets the **mean**; turn it off for strictly MAPE-optimal points. Divergence guard: if a fit still blows up in log space (the forecast saturates the explosion clip on a majority of the horizon — seen on real spiky weekly data as a flat ~3.8e6 forecast at ~1400% MAPE, from a near-explosive AR root or exogenous extrapolation), `predict()` raises `ModelPredictionError` so the orchestrator drops the model into `evaluate_errors`/`forecast_errors` rather than emitting a degenerate flat-line "result" that pollutes the comparison and plots. (This is distinct from a merely-inaccurate model, which stays a real result and is excluded by the ensemble MAPE threshold.) `save`/`load` use the default pickle (statsmodels serialises reliably). No orchestrator changes were needed — it plugged into `evaluate()`/`forecast()`/ensemble/export/plot through the existing contract. (Phase 6, Part 1)

- **Annual-collinearity warning for SARIMAX exog** (`SARIMAXAdapter._warn_on_annual_collinearity()`). When a declared independent column strongly tracks the annual cycle — measured as the R² of an OLS fit on a sin/cos annual basis, flagged at ≥ 0.30 — the adapter warns at `transform_train()`. Such a column explains much of the same variance as SARIMAX's annual Fourier terms, so on short histories the two compete: a good low-Fourier fit can collapse once the column is added, and the grid is pushed toward a lower `fourier_order_annual`. Diagnostic only (nothing is dropped or altered) and fires once per model fit. Prompted by real weekly data where a seasonal stockout-weighting column roughly doubled the best achievable SARIMAX MAPE versus the same run without it — not a bug, an inherent identifiability limit on ~100 rows, which the warning now surfaces instead of leaving buried in the grid summary. The scorer is phase-invariant (a seasonal driver is flagged whatever its peak week) and the 0.30 threshold is calibrated to flag such a driver while leaving ordinary trending spend columns silent. (Phase 6, Part 2 hardening)
- Two new `forecast()` safety warnings, both model-agnostic and prompted by real-dataset testing: (1) when `future_independent_data` isn't supplied, a warning naming the auto-generated columns and horizon, since an exogenous-driven forecast can be dominated by invented inputs and this was previously silent; (2) `_warn_on_forecasts_far_outside_history()`, which flags any model whose forecast peaks more than 50% above (or bottoms 50% below) anything ever observed in the target. The margin is deliberate — a trending series legitimately forecasts past its historical max, so a plain "outside the historical range" rule would fire constantly. (Phase 6, Part 1 hardening)
- `exporters.py` now writes five CSVs instead of three, adding `{prefix}_final_best_model.csv` (the single lowest-MAPE model's forecast, via `build_best_model_forecast_table()`) and `{prefix}_model_summary.csv` (per-model MAPE, ensemble weight and status, plus an `ensemble` row, via `build_model_summary_table()`). Because a weighted ensemble is not guaranteed to beat the best individual model, both "final" candidates are exported side by side with the scores needed to choose, rather than baking the choice in. `export_forecast_csvs()`/`export_forecast()` gained `per_model_mape=` and `ensemble_mape=` to drive them. (Phase 6, Part 1 hardening)

- **NeuralProphet** (`data_adapter/neuralprophet_adapter.py`, `models/neuralprophet_wrapper.py`, `neuralprophet:` config block, registered in `MODEL_REGISTRY`): the fourth model. The adapter is stateless and passes the target and regressors through **raw** — NeuralProphet normalises internally, so the SARIMAX-style log/standardise/clamp treatment would double-normalise. Uses the standard forecaster grid search (`learning_rate` × `epochs`, 4 candidates). Deliberate choices: `n_lags=0` (no autoregression) in v1, because NeuralProphet fixes `n_forecasts` at construction while `BaseModel` is fit-once/predict-any-horizon, and an AR model scored against a frame containing real test actuals is not comparable to the other models (it would be over-weighted by inverse-MAPE ensembling); the future frame is built directly from `future_exog` with `y=NaN` rather than via `make_future_dataframe()`, so the wrapper retains **no training history** and `save`/`load` stays a clean model-only operation; CPU pinned and NP/Lightning logging silenced so local (MPS) and CI (CPU) runs agree; `epochs` and `learning_rate` both pinned (leaving either `None` triggers a learning-rate range test and auto-sized epochs — slow and non-reproducible); `yearly_seasonality="auto"` rather than forced `True`; non-negative clipping is data-driven (mirroring `CatBoostWrapper`); seeded via `set_random_seed`, since NeuralProphet is stochastic and drifts between runs otherwise. `save`/`load` overridden (torch state). No uncertainty bounds in v1, per `models/base.py`'s contract note. (Phase 6, Part 2)

- **Bayesian PyMC** (`data_adapter/bayesianpymc_adapter.py`, `models/bayesianpymc_wrapper.py`, `bayesianpymc:` config block, registered in `MODEL_REGISTRY`): the fifth and final model — a Bayesian structural time-series model (linear trend + annual Fourier, plus a weekly Fourier cycle for daily data, + a linear regression on the standardised independent columns, under a Student-T likelihood) sampled with NUTS. Completes the model set; no orchestrator change was needed, so the `BaseModel`/`BaseAdapter` gate rule held across all five models. The adapter is stateful like SARIMAX's (raw `y` + standardised exog + a train-range clamp on future exog) but without the log1p or the collinearity warning; the target z-scoring and the Fourier basis live in the **wrapper** (same split reasoning as SARIMAX), so `y` keeps one raw meaning and the Fourier order is grid-searchable. `predict()` **reconstructs `mu` from the stored posterior draws in pure numpy** (a fit-once/predict-any-horizon linear combination of the sampled coefficients) rather than re-running the sampler or slicing a whole-series `Deterministic` as the reference notebook did — so prediction honours the contract's split and never imports pymc. Coefficient priors are chosen per column with no metadata channel: a continuous driver (>2 distinct standardised values) gets an informative prior centred on its OLS slope against the target, a binary flag gets a zero-centred prior. Emits a **posterior-predictive band** (`yhat_lower`/`yhat_upper` = 3rd/97th percentiles of draws from `y ~ StudentT(nu, mu, sigma)`, i.e. mean-function uncertainty plus observation noise), making it the third bounds-emitting model with Prophet and SARIMAX. (An initial cut banded the latent mean `mu` alone, as the reference notebook did; real-data diagnostics showed that under-covered badly — ~34% of daily actuals inside a nominal 94% band — so it was corrected to sample the likelihood, which restores coverage toward nominal without changing the point forecast or MAPE.) `save`/`load` overridden: the PyMC `InferenceData` is written to a NetCDF sidecar and the rest pickled, so predictions reload exactly from the pickled numpy posterior. **Daily is tuned for scale**: on ~1000+ rows, exog that tracks the annual cycle (the overlap SARIMAX already warns about) makes NUTS take deep, slow leapfrog trajectories, so the daily config halves draws/tune to 1000 (which barely moves the point forecast — a 4× draw sweep moved MAPE <0.2pp), caps the Fourier order at 4, and **grid-selects `beta_fourier_sigma` (0.3 tight vs 1.0 loose)** so the data chooses how tightly to regularise the Fourier basis — neither value is universally better, so like `n_fourier` it belongs in the grid. Weekly samples cleanly at the notebook's 2000/2000. Verified in-sandbox (pymc installs there, unlike torch): real daily result 18.09% MAPE, second only to SARIMAX. (Phase 6, Part 3)

### Changed

- **Widened NeuralProphet's config to cut its under-fitting.** The synthetic sweep showed NeuralProphet was the consistent outlier — e.g. 18.7% MAPE on a mid-series level shift vs ~2% for the structural models, which fit these clean parametric signals near-perfectly. Root cause was under-fitting: too few epochs for an SGD-trained neural model to converge, and too little trend flexibility to track a level shift. So its grid now spans a **middle learning rate** (`0.03`, alongside `0.01`/`0.10`) and **higher epochs** (`150`/`300`, up from `50`/`150`), and the trend gets **more changepoints** (`n_changepoints` 20 daily / 10 weekly, `changepoints_range` kept at the 0.8 default), so a level shift is tracked rather than smoothed over. The grid still selects by test MAPE, so a setting that overfits a given dataset isn't chosen; `n_lags` stays 0 (the comparability constraint). Confirmed on the synthetic sweep: `regime_shift` dropped from 18.7% to 1.8% (in line with the others). An interim try with `changepoints_range=0.9` regressed a smooth-trend series (`negative_effect_driver`) by letting late changepoints extrapolate a noisy final trend segment, so the range was left at 0.8. Trade-off: 6 candidates (up from 4) at more epochs makes NeuralProphet slower per run. (Phase 8, real-dataset testing)
- **The default future-exogenous-data behaviour changed from replay-the-tail to `carry_forward`.** When `forecast()` isn't given future driver values, it previously replayed the last `horizon` periods of history (cycling if the horizon exceeded it), which injects the recent pattern — including any one-off spike — into the future. The default is now `carry_forward` (hold the last value flat), the least-surprising neutral baseline. The old behaviour is still available explicitly as `future_exog_strategy="cycle"`. This changes `forecast()` output only when independent columns are declared *and* no future values are supplied. The internal `HorizonForecaster._build_default_future_independent_data()` was removed in favour of `future_exog.resolve_future_exog()`; two tests that asserted the old cycling were re-pointed at the `cycle` strategy. `ForecastResult` gained a `future_exog_used` field (defaulting to `None`). (Phase 7)
- **`_run_hyperparameter_grid_search()` now tolerates per-candidate failures.** Previously any single candidate raising killed the whole model; now failures are skipped, a `UserWarning` names how many were dropped and why, and the model itself fails only if *every* candidate fails (leaving other models untouched, as before). When all candidates fail **the same way**, the original exception is re-raised unchanged rather than wrapped: an identical failure across every candidate is not hyperparameter-specific, so relabelling it would be wrong — a plain "not enough rows" must stay an `InsufficientDataError`, keeping its `required_periods`/`available_periods` for callers that branch on type. Only genuinely mixed failures, where no single type is representative, become an aggregate `ModelConvergenceError` naming every distinct cause. Model-agnostic: an invalid CatBoost depth or a diverging SARIMAX order no longer costs you a model that had other working candidates. (Phase 6, Part 2 hardening)
- **SARIMAX switched from internal self-tuning to the standard grid search**, so all four models are now selected the same way. Its wrapper previously ran an ADF + validation-MAPE search over orders and carried no `hyperparameter_grid`. That was more statistically honest — it never saw the test split — but it made SARIMAX the only model selected differently: Prophet/CatBoost/NeuralProphet all score candidates *on the test split*, so their reported MAPE is optimistic while SARIMAX's was not. Comparing those numbers head-to-head, and deriving inverse-MAPE ensemble weights from them, systematically penalised SARIMAX for being more rigorous. The grid now varies `(p, q)`, seasonal `(P, Q)` and `fourier_order_annual`; `d` stays ADF-derived. Trade-off accepted knowingly: SARIMAX's MAPE becomes optimistic like the others, and each candidate is now a full fit rather than the old cheap `maxiter=30` search. (Phase 6, Part 2 hardening)
- **Annual Fourier generation moved from `SARIMAXAdapter` into `SARIMAXWrapper`**, where it becomes an ordinary grid-searchable hyperparameter (`fourier_order_annual`, `0` = off) instead of a hardcoded module constant gated by a coverage rule. Real data forced this: on a ~3-year daily series annual Fourier was a clear win, but on a ~2-year weekly series it was *actively harmful* (82.81% at order 2 vs 48.74% with none) and diverged outright at order 10 — no fixed default serves both, so the data has to choose. Terms are now built from **absolute day offsets** against a fit-time reference date rather than a positional index, making them robust to gaps in the date sequence. (Phase 6, Part 2 hardening)
- Horizon-vs-history warning tightened: it now fires once the horizon exceeds **half** the available history (`_HORIZON_WARNING_FRACTION = 0.5`), replacing a rule that only fired above **twice the entire history**. The old threshold let a 100-period forecast from 121 periods of data pass silently — the exact case that produced an implausible real-world forecast. (Phase 6, Part 1 hardening)
- `{prefix}_final.csv` renamed to `{prefix}_final_ensemble.csv`, now that a best-single-model "final" is exported alongside it. (Phase 6, Part 1 hardening)
- Pinned all previously-unpinned dependencies; added `requires-python` constraint. (Phase 2, packaging hardening)
- Added a CI test matrix across Python 3.10–3.12, catching a `matplotlib` version incompatibility and a `setuptools 82` regression (`pkg_resources` removed). (Phase 2, packaging hardening)
- Added explicit `[tool.setuptools.packages.find]` include list to prevent stray local folders (e.g. `test_env/`) from being mistaken for a second top-level package. (Phase 2, packaging hardening)
- **Breaking:** `HorizonForecaster.evaluate()`/`.forecast()` now always return a `Dict[str, EvaluationResult]`/`Dict[str, ForecastResult]` keyed by model name, even when only one model is requested — previously returned a single result object directly. (Phase 3)
- `BaseAdapter.__init__()` now accepts a uniform `frequency` parameter (used by `CatBoostAdapter`, ignored by `ProphetAdapter`) so `forecaster.py`'s `MODEL_REGISTRY`-driven adapter instantiation stays identical across every model, with no per-model special-casing in the orchestrator. (Phase 3)
- `CatBoostWrapper.min_rows_required` is now a plain training-row-count floor, identical in meaning to `ProphetWrapper`'s — previously it applied to rows remaining *after* `CatBoostAdapter`'s lag-warmup drop, a mechanism that no longer exists. (Phase 3)
- `publish.yml` switched from `twine` + long-lived `PYPI_API_TOKEN` secrets to PyPI Trusted Publishing (OIDC via `pypa/gh-action-pypi-publish`) — no stored credentials, short-lived per-run tokens instead. Manual `workflow_dispatch` runs now take a `target` input (`testpypi` default / `pypi`), so a manual run defaults to a safe TestPyPI dry run rather than a real release; tag pushes (`v*`) still always publish to real PyPI.

### Fixed

- **A model raising an unexpected (non-`HorizonForecaster`) error aborted the whole `evaluate()`/`forecast()` run** instead of being isolated. Found via the synthetic-dataset test sweep: a dataset with NaN in the target/driver made `BayesianPyMCWrapper.fit()`'s prior-estimation `np.polyfit` raise a raw `numpy.linalg.LinAlgError` *before* the sampler's guard, and because it wasn't a `HorizonForecasterError`, the orchestrator's per-model `except HorizonForecasterError` didn't catch it — so it propagated and took the other four models' results down with it. Fixed on two levels: (1) `evaluate()`/`forecast()` now isolate **any** per-model exception, recording a non-typed failure as `ModelConvergenceError` (with the original exception preserved via `original_exception`) in `evaluate_errors`/`forecast_errors`, so one model can never abort the rest; (2) PyMC's prior estimation is now NaN-safe (`_ols_slope` drops non-finite pairs) so it can't leak a raw error in the first place. (That specific NaN trigger is now additionally blocked up front by the complete-data requirement above; the isolation fix is the general guarantee, independent of the NaN case.) (Phase 8, real-dataset testing)
- **NeuralProphet failing to fit at all** with `ConfigValueError: Unions of containers are not supported: loss_func: Union[str, _Loss, Callable]`, taking the model out of affected runs entirely. Fixed by setting `collect_metrics: false` in both frequency blocks of `config/default_params.yaml`. NeuralProphet attaches a PyTorch Lightning logger whenever metrics are enabled (`configure_trainer()` sets `config["logger"] = metrics_logger`), and a logger makes `trainer.fit()` run `_log_hyperparams()` → `logger.save()` → `save_hparams_to_yaml()` → `OmegaConf.save()`. OmegaConf then rejects `ConfigTrain`'s `loss_func: Union[str, _Loss, Callable]` and `fit()` dies before training. With metrics off, `configure_trainer()` sets `logger = False` and that path never executes. Nothing is lost: MAPE is computed by the orchestrator, which never reads NeuralProphet's training metrics, and NeuralProphet's own documentation notes that collecting them slows training. **No dependency pin changed** — both alternatives were checked against the actual package sources and neither works: NeuralProphet 0.9.0 carries the identical annotation, and no omegaconf version is viable (≥ 2.2 rejects unions of containers, while 2.1.x is stricter still and rejects *every* Union). Since neither NeuralProphet nor Lightning *declares* omegaconf, it arrives transitively, which is why this reproduced in some environments and not others. (Phase 6, Part 2 hardening)
- **`NeuralProphetWrapper.load()` returning a model that failed on the next `predict()`** with a bare `AttributeError: 'NoneType' object has no attribute 'predict'`. NeuralProphet's `save()` deliberately nulls `forecaster.trainer` and `forecaster.model._trainer` (a PyTorch Lightning `Trainer` isn't picklable) and its `load()` rebuilds one via `restore_trainer()`; the `torch.load` fallback added for the PyTorch ≥ 2.6 `weights_only` flip skipped that step, so the model reloaded structurally complete but unusable, failing later and far from the real cause. The fallback now mirrors `np_load()`'s post-load step. Both failures on this method were CI-only for the same structural reason — local torch is < 2.6, so the fallback branch never executes locally at all — so `tests/test_neuralprophet_compat.py` now stubs `neuralprophet` and `torch` into `sys.modules` and drives that branch directly on any torch version, including environments without torch. (Phase 6, Part 2 hardening)
- Non-reproducible Prophet uncertainty intervals (`yhat_lower`/`yhat_upper` varied across calls on an identical fitted model) — root-caused to Prophet's unseeded uncertainty simulation, fixed with an explicit, overridable random seed. (Phase 2)
- `config/default_params.yaml` missing from the built wheel despite working in editable installs. (Phase 2, packaging hardening)
- Fixed hyperparameter combinations producing broken forecasts (MAPE up to 802%, including negative predictions) on short-history datasets — resolved by adding safe `auto`-based fallback candidates to the grid search rather than a hand-coded data-span rule. (Phase 2, real-dataset testing)
- Test-split construction bug: the chronological test split was built by calling `transform_train()` on the held-out test rows in isolation. This worked incidentally for the stateless `ProphetAdapter`, but would have silently corrupted `CatBoostAdapter`'s stateful lag/rolling features (computed from the short, disconnected test split instead of real training history). Fixed by calling `transform_train()` once on the training data, then `transform_future()` (which reuses retained history) to build the test split's features. (Phase 3)
- `training_size` leaving zero evaluation rows now raises `InvalidConfigError` immediately at construction instead of inside per-model evaluation, where the new partial-failure handling would have silently swallowed it and misreported it as `AllModelsRejectedError` instead of the real, dataset-level configuration problem. (Phase 3)
- Missing coverage branch in `CatBoostAdapter`'s insufficient-history check (`rolling_windows` path was never exercised, since the existing test's `lags` check always failed first). (Phase 3)
- **CatBoost long-horizon accuracy**: the original `CatBoostAdapter` design (lag(1/2/3/7/14) + rolling(7/14) target-history features, frozen at train-end and broadcast unchanged across the whole forecast horizon — necessary because `CatBoostWrapper.predict()` is one batched call, not a per-step recursive loop) produced catastrophic MAPE on real data whenever the horizon crossed a sudden target level-shift: 52.6% MAPE in the first half of a 144-day test window vs. 27.3% in the second half, and 67-90% MAPE specifically on a real, flagged demand-dip period vs. 34-40% on ordinary days — because a frozen snapshot of "recent history" has no way to see a spike or dip coming and keeps predicting the pre-shift baseline for the entire horizon. Root-caused by comparing against an independently-built, dedicated CatBoost reference notebook against the same dataset (~16% MAPE, no such failure mode) that used a trend index + cyclical seasonality instead of lag/rolling features. Fixed by replacing the feature set entirely (see Added above) rather than tuning around the symptom. **Confirmed post-fix on the same real dataset** (90% training size): overall MAPE 18.86% (vs. Prophet's 18.68%, essentially matched, down from a pre-fix 39.95-45.47%); flag-segment breakdown showed December_Dip at 14.59% MAPE — down from 67-90% pre-fix, now the *best*-performing segment rather than the worst — with BFCM at 21.97% and all other days at 19.82%, all in a normal, tight range. (Phase 3, real-dataset testing)
- `CatBoostWrapper._categorical_feature_names` is now always empty — no calendar feature is declared categorical, matching the working reference notebook (which used none) rather than the original, untested categorical-encoding assumption. (Phase 3)
- Fixed `CatBoostWrapper.save()`/`.load()` silently dropping the new non-negative-clipping decision (`_target_min`) on a reload — caught while adding the feature, before it shipped as a real bug. (Phase 3)

### Known limitations

- **Ensemble weighting is not guaranteed to beat the best individual model** — this is a real, permanent characteristic of the design, not a bug to be fixed. Confirmed via direct testing (not assumed): even inverse-MAPE weighting can produce an ensemble MAPE worse than the single best model — on a synthetic test, Prophet alone scored 1.31% MAPE, CatBoost alone 12.77%, and the ~91%/9%-weighted ensemble of the two scored 1.58%, worse than Prophet alone. Root cause: weights are static across the whole horizon while each model's real per-period error isn't, so an otherwise-strong ensemble can still get dragged down on the specific periods where the weaker model is wrong. Documented directly in `evaluation/ensemble.py`'s docstring as a load-bearing finding — this is why `evaluate()`'s `EnsembleResult.mape` is computed and surfaced against real actuals rather than assumed, so the ensemble's own accuracy can always be checked against each individual model's before trusting it. (Phase 4)

### Known deferred issues

- 24 CVEs in `torch`/`pytorch-lightning`, forced by `neuralprophet==0.8.0`'s own version constraints — consciously deferred rather than pinning an untested pre-release NeuralProphet. **Still open:** NeuralProphet remains pinned at `0.8.0`, so these stand until a vetted newer NeuralProphet (with relaxed torch constraints) is adopted.
- **Publishing is deferred to a dedicated release stage** — none of the following is a bug, just work that only makes sense once the package goes public:
  - wire `.github/workflows/publish.yml` (already written, gated behind a manual trigger / version tag) to a PyPI Trusted Publisher;
  - add PyPI-facing metadata to `pyproject.toml` — `authors`, `keywords`, Trove `classifiers` (Python versions, license, topic, dev status), and `[project.urls]` (Homepage / Repository / Changelog);
  - re-export the public API from the top-level `horizon_forecaster/__init__.py` so `from horizon_forecaster import HorizonForecaster` works (the subpackage `__init__.py` files stay empty — they only mark packages for discovery);
  - replace the empty `examples/*.md` placeholders with runnable daily/weekly Colab notebooks (clean `pip install horizon_forecaster` + an "Open in Colab" badge), reusing the drafted walkthrough content.
- **Bayesian PyMC is substantially slower than the other four models** — it runs a full NUTS/MCMC sample per grid candidate. This is inherent to the approach, not a bug; the daily config is tuned to keep it practical (halved draws/tune, capped Fourier order, grid-selected Fourier-prior regularisation — see the Part 3 entry above), but a full daily run is still a matter of minutes, not seconds. Restrict `models=` to exclude it, or pass a small-draw `model_params` override, to iterate quickly. `nutpie` (a faster compiled CPU NUTS backend) is a possible future speedup, not adopted in v1.
- All five models are now registered in `forecaster.py`'s `MODEL_REGISTRY` (SARIMAX Part 1, NeuralProphet Part 2, Bayesian PyMC Part 3), each absorbed with no orchestrator change as designed. The ensemble has now been exercised end-to-end on a real **five-model** run (daily: PyMC 18.09% MAPE, second only to SARIMAX at 17.73%).
